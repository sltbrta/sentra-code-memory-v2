## Why this file exists

A 13-agent review produced 166 findings. Per the review policy this repository
works under, that output is **candidate generation, not a verdict**:

> Deterministic tests, validators, and other executable checks are the decision
> layer. LLM review is advisory candidate generation only: it cannot override a
> failed check or replace missing evidence. Every candidate finding must state a
> reachable input/trigger, current wrong output, expected output, and a concrete
> executable check. It remains advisory until that check confirms or falsifies
> it.

So each row below records what actually happened when the claim was executed.

## Dispositions

| Code | Meaning |
| --- | --- |
| `CONFIRMED` | A test reproduced it against the base, then passed after the fix. |
| `FALSIFIED` | The claim did not reproduce. Discarded, with the killing evidence. |
| `DECISION` | Real, but the remedy is a product call. Entry in `DECISIONS.md`. |
| `DEFERRED` | Real, remedy known, not in this pass. Entry in `HARDENING.md`. |

A `CONFIRMED` row is only complete when its red-proof command and output are
recorded. A fix without a test that failed first is not evidence.

`FIXED-UNPROVEN` was added after a fresh-eyes review audited this table and
found rows marked `CONFIRMED` whose fix could be reverted with the suite staying
green. The fixes were real and had been verified by reading; what was missing
was an executable check that would catch a regression. Calling those
`CONFIRMED` was the same overclaiming this branch exists to remove, so they
were relabelled rather than left flattering.

All fifteen now carry a guard, and every guard was run against its reverted fix
and observed to fail before being recorded. No row currently holds this status.
Writing them turned up four defects the original fixes had missed, each fixed
in the same commit as its guard: three files still published 0644 under D-007,
C-009 recorded its failure in a field that was populated exactly when the
failure did not matter, and the sidecar writer never saw the full-rewrite flag
the corpus branch had already cleared.

Two rows previously cited red proofs that did not happen. `R-003` named a test
that never called `flush` — it reimplemented the *fixed* logic inline and
asserted that copy did not race — and `C-002` named a test that never induced a
panic. Both tests passed with their fix entirely removed. Both have been
rewritten and genuinely red-proved; the corrected evidence is in their rows.

`ontology.extractMentionTokens` is the one of the sixteen that was **not** a
defect, and proving that is what found S-003.

The first attempt asserted its output was valid UTF-8, passed against the
unfixed code, and was deleted rather than kept as evidence it was not. The
claim was then narrowed to something provable -- that switching the site to
`textbound` changed nothing -- and a differential fuzz test was written to
prove it. **It failed in 46 seconds**, on invalid-UTF-8 input, because the
claim was false: `textbound.Bytes` was emptying such input. Fixing S-003 made
the claim true, and 10.2 million fuzz executions now find no counterexample.

The lesson is worth recording next to the row: an unproved claim was left
standing as "fixed for consistency", and the only reason it was not shipped as
true is that someone tried to prove it.
